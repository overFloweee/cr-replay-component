# CR Replay Component

**English** | [简体中文](README.zh-CN.md)

CR Replay Component is a local Clash Royale replay component for Android. It brings together replay input validation, rule selection, resource preparation, native core integration, and playback process management, with a minimal Android example host and local build tools.

The externally supplied game core performs combat simulation and rendering. This project provides the integration code and build tools; a complete build also requires game materials that match the registered digests.

## Features

- **Input validation and rule selection**: Check replay structure, version identifiers, and supported commands; select rules from the bundled registry; reject unknown versions and conflicting inputs.
- **Resource preparation**: Validate the complete resource archive and its entries, including digests, sizes, and paths, then prepare the required content in app-private storage.
- **Separate playback process**: Use a separate run directory and launch ticket for each playback, start the game host in the `:replay` process, record outcomes, and reclaim directories after their runs have exited.
- **Native core bridge**: Connect to the fixed core through JNI, submit replay input, observe playback state, and calculate terminal crown counts.
- **Local builds and checks**: Restore the registered core from external materials, generate rule and visual bundles, build the example APK, and run host checks with synthetic data.

The example host provides a local playback entry point. It has no account system, cloud archive, resource downloader, or remote catalog service. Android integration source is in `android/` and is compiled directly; no Maven or AAR package is provided.

## Build the example application

### Requirements

- Python 3.9+. Do not enable `-O`, `-OO`, or `PYTHONOPTIMIZE`; core recovery relies on integrity assertions.
- JDK 17+, including `java`, `javac`, and `keytool`.
- Android SDK: Platform 36, Build Tools 36.0.0, and NDK 27.1.12297006.
- An externally installed Apktool 3.0.3 JAR.
- Host checks also require `clang++`. The example targets Android 11 / API 30+ on `arm64-v8a`.

The build script selects toolchain paths for macOS and Linux. The recorded complete build was performed on macOS.

### Prepare external materials

Follow the [materials list](docs/materials.md) to supply the exact APK, runtime snapshots, symbol and export information, historical rule materials, and a separate animation JSON file. Core and content input identities are registered in [`metadata/supported_engine.json`](metadata/supported_engine.json).

**The game APK alone is insufficient to build the project.** This repository provides neither material downloads nor a complete acquisition workflow. The build fails if a required input is missing or its digest differs.

### Run the build

```sh
python3 tools/build.py \
  --input-root /path/to/local-input-root \
  --visual-source /path/to/asm_hero_electrowizard_battle.json \
  --apktool /path/to/apktool-3.0.3.jar \
  --sdk /path/to/android-sdk
```

`--input-root` points to a local directory containing `materials/`; see the materials list for its layout. The build validates registered inputs, restores the core, generates resource and rule bundles, compiles Java and the native bridge, packages and signs the APK, then checks its signature and embedded bundles.

Main outputs are written to `build/local/`:

| File | Purpose |
| --- | --- |
| `ReplayComponent.apk` | Example application signed with a local development key |
| `resources.pack` | External resource archive paired with this build |
| `resource-registration.json` | Digest, size, and runtime-size registration for this resource archive |
| `replay-rules.zip`, `replay-visuals.zip` | Generated rule and visual bundles |
| `build-proof.json` | Build source digests, output identities, and verification status |

A development key is generated in `.local/` on the first build for local development use. Both `build/` and `.local/` are ignored by Git. Use the APK and resource archive generated by the same build together. The historical registration in `metadata/public_resources.json` does not identify a newly generated archive.

The builder refuses to reuse an existing `build/local/decoded` directory. Before rebuilding, preserve any logs and evidence you need, then clean up the rebuildable decoded directory and packaging intermediates.

## Play a local replay

Prepare a compatible Android device or an existing emulator. Replace `SERIAL` with an explicit ADB device serial:

```sh
adb -s SERIAL install -r build/local/ReplayComponent.apk
adb -s SERIAL shell am start -n org.crreplay.example/cn.crhistory.player.ExampleActivity
adb -s SERIAL shell mkdir -p /sdcard/Android/data/org.crreplay.example/files
adb -s SERIAL push build/local/resources.pack /sdcard/Android/data/org.crreplay.example/files/resources.pack
adb -s SERIAL push /path/to/replay.json /sdcard/Android/data/org.crreplay.example/files/replay.json
```

Tap **Play local replay** in the example UI. The app imports and validates the resource archive, saves an input copy, selects rules, and starts the separate playback process. Replay files are limited to 16 MiB. Supply your own real replay files; none are distributed with the repository.

After returning, starting another replay records an outcome summary for an exited run and reclaims its directory. Summaries are stored in app-private `files/replay/evidence/`. Full telemetry and result files remain in the run directory; export them before the next reclamation if you need them for analysis.

The example does not generate an independent expected score. Validating a real replay requires a separate, trustworthy match result and a reference for comparing the match process.

## Run host checks

```sh
ANDROID_HOME=/path/to/android-sdk python3 tests/check.py
```

Checks use synthetic data and write their outputs to `build/local/tests/`. The first run downloads the test-only `org.json:json:20180813` dependency and verifies its pinned SHA-256 before use.

Coverage includes version mapping and rejection conditions, rule and visual bundle failure cleanup, resource paths and digests, the 2 GiB boundary using actual expanded streams, archive determinism, 12 native terminal-result fixtures, and rejection of Python optimization mode.

A complete build and host checks have passed; see the [verification record](docs/review.md). Actual Android playback and the independent example host's return and restart lifecycle still require device verification.

## Compatibility and limitations

The integration targets the fixed, registered Chinese-server 38.4.2 core. It includes seven rule snapshots—38.4.3, 38.4.5, 38.4.6, 38.4.8, 38.4.9, 38.4.10, and 38.4.11—and a small number of explicit aliases. The number of rule snapshots does not imply support for the same number of independent game cores or verification of every mode in those versions.

Version registrations and synthetic checks establish the corresponding selection and rejection behavior. Some registrations are still marked as not ready; unknown combinations are rejected. See the [compatibility notes](docs/compatibility.md) for the specific conditions.

Resource preparation validates the complete archive and its entries, but protection against changes to all materials during playback has not been established. Matching terminal crown counts also does not establish identical combat timing, object trajectories, or visual output.

The native adaptation includes core-specific addresses, structure offsets, short instruction signatures, and hooks. Build tools generate or modify smali in the externally supplied client. Changing game versions requires rechecking core identity and adaptation conditions.
